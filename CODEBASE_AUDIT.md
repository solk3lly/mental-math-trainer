Reviewed 14 November 2026 against the working tree at `ff90be917d9f26d9928021711425cb4a5fec7192` (`Fix progress persistence and account preference sync`). At the start of the audit, 95 tracked files had line-ending changes and three local review scripts were untracked. The tracked diff was empty with end-of-line whitespace ignored. ## Confirmed findings

### 1. A failed account reset deletes unsynced answers · High

If an account has pending answers and the cloud delete fails, the user sees a reset error but loses their pending progress. The coordinator increments the generation and drops registered buffers before invoking reset work. The dashboard then clears the durable queue before issuing the delete. Neither path restores pending data on failure. A focused check with a rejecting reset callback observed zero later uploads for one queued answer. The two cloud tables also reset in separate requests, so an administrator can receive an error after one table has already been cleared. Preserve pending rows on failed deletion and make the cloud reset atomic. [Coordinator, lines 46–59](utils/progressWriteCoordinator.js#L46) · [Dashboard, lines 189–207](pages/stats.js#L189) · [Buffer discard, lines 496–500](utils/progressLogs.js#L496)

### 2. An old buffered row causes new answers to be dropped after another tab resets · High

Both log buffers take the whole batch out of memory and use only its first row's generation to acquire the write lock. If a tab queues one answer before another tab resets, then queues a second answer after the reset but before flushing, the stale first row causes the coordinator to skip the entire write. A focused check against the AI buffer expected the post-reset answer and observed zero writes and `flushedCount: 0`. That buffer has no durable queue, so the answer is lost. The manual buffer can leave later answers in IndexedDB for replay, but both trainers can report a successful cloud save because their finalizers ignore the flush outcome. Filter or group by owner and generation inside the lock, then use a per-session acknowledgement to report the save result. [AI flush, lines 235–255](utils/aiModeLogs.js#L235) · [Manual flush, lines 432–456](utils/progressLogs.js#L432) · [Generation check, lines 31–38](utils/progressWriteCoordinator.js#L31) · [Standard summary, lines 443–450](pages/index.js#L443) · [Mixed summary, lines 362–365](pages/mixed.js#L362)

### 3. Offline work on another device can restore reset history · High

Reset coordination covers one browser origin. An account's pending answers on another device or browser profile survive a successful reset and can be uploaded later when that profile opens Progress. Durable entries contain the owner and row, and replay checks authentication before upserting. The backend's ordinary insert policy checks ownership, and the reset stores no account-wide cutoff that could distinguish pre-reset work. The reset promise to delete account progress needs a server-side generation or cutoff that the server validates on both normal writes and replay. [Browser-scoped coordination, lines 12–23](utils/progressWriteCoordinator.js#L12) · [Durable queue, lines 297–328](utils/progressStorage.js#L297) · [Replay, lines 50–67](pages/stats.js#L50) · [Insert policy, lines 62–64](supabase/migrations/20260313_create_progress_logs.sql#L62)

### 4. The documented self-hosted web setup locks an affected Next.js version · Medium

The lockfile resolves Next.js `15.5.28`. The upstream advisory rates the SVG rejection bypass in the self-hosted image optimizer moderate and identifies `15.5.29` as fixed. The documented `next start` configuration keeps the framework's default optimizer route enabled. The application serves its images directly. This confirms the affected dependency and route configuration. Whether a deployed optimizer is reachable under the advisory's conditions remains unverified. Update the lockfile to a patched release and disable the unused optimizer. The Android export has no Next.js image server. Two other November advisories cover the locked version but require App Router fetch response forwarding or Edge routes that set cookies. Those entry points are absent from the reviewed web tree. ### 5. Pending-upload errors hide readable account history · Medium

Progress awaits replay before it requests the dashboard. If a pending batch fails with a write-specific error, such as a schema or row constraint rejection, the catch path replaces the dashboard with an empty snapshot and renders a load error. Every refresh retries the same batch first. Fetch the account dashboard independently of queue replay and show a retryable sync error alongside the history. [Progress load and replay, lines 50–90](pages/stats.js#L50) · [Batch error propagation, lines 256–290](utils/progressLogs.js#L256)

### 6. A stale import completion can take over the dashboard after an account switch · Medium

`handleImport` verifies ownership during upload, including immediately before its final local import marker. An account change during that final awaited storage operation still allows the old handler to clear the offer and call its closed-over `loadLogs`. That call increments the shared sequence after the new account's load has started, so the new account's request can be ignored. The old function can then commit an empty snapshot or error under the new account. The same owner guard should cover import completion, the dashboard load it starts, and writes to import state. Tag rendered results and offers with the owning account. [Sequence handling, lines 71–112](pages/stats.js#L71) · [Import completion, lines 143–170](pages/stats.js#L143)

### 7. Guest recovery can make a live round selectable for import · Medium

A guest round in a backgrounded or suspended tab can miss its five-minute heartbeat. Progress marks the round interrupted. When the trainer resumes, its heartbeat updates only `active` rows, and accepted attempts update the timestamp without restoring the active state. Another tab can offer that still-running round for import. If it is imported and retired, later answers in the trainer fail the `importedTo` guard. Revalidate liveness when a tab resumes and atomically check the current state when claiming a session. Keep any recovered live session out of import and pruning while it still has a writer. [Heartbeat registration](pages/index.js#L254) · [Heartbeat and recovery, lines 170–207](utils/progressStorage.js#L170) · [Attempt write, lines 91–126](utils/progressStorage.js#L91) · [Import claim, lines 283–294](utils/progressStorage.js#L283)

### 8. Blocked IndexedDB opens can leave a connection that blocks later upgrades · Medium

`onblocked` rejects the open promise and clears the cached promise. The original request stays pending. If the blocking tab later closes, that request can succeed but its resolution is ignored, leaving an untracked connection open. Even successful cached connections have no `versionchange` handler. A tab holding either connection can prevent another tab from upgrading or deleting the database until the connection closes. Close late successful opens after rejection, and close and invalidate the cached connection when IndexedDB signals a version change. [Open lifecycle, lines 28–57](utils/progressStorage.js#L28) · [IndexedDB specification](https://w3c.github.io/IndexedDB/#dom-idbdatabase-onversionchange)

### 9. Account tables have no ongoing 90-day deletion · Medium

The migration performs a one-time delete for each progress table. The dashboard filters its queries to 90 days and new inserts can continue aging in storage. The tracked schema and scheduler inventory contain no recurring purge. The README says that the migrations create retention rules, but the account implementation only provides a reporting window after cutover. If a separate production purge exists, verify it and document its owner. Otherwise, implement scheduled deletion or describe this as a reporting window and specify the actual storage policy. [README, lines 103–107](README.md#L103) · [One-time deletes, lines 19–40](supabase/migrations/20260418010000_enforce_exponent_cutover_and_90_day_retention.sql#L19) · [Dashboard filters, lines 104–128](supabase/migrations/20260418010000_enforce_exponent_cutover_and_90_day_retention.sql#L104)

### 10. Simultaneous preference edits can overwrite unrelated settings · Medium

Each tab merges a patch into its current local snapshot and sends a full row. For example, a tab changing display mode can write its stale theme over another tab's recently saved theme. The database increments `revision` for that write, so both clients treat the overwritten row as newest. Mixed preferences also send a full row. Send only changed fields for an existing row or use a revision precondition and merge onto the latest row before retrying. First-time preferences should insert only if the row is absent, since two devices can otherwise both see an empty result and overwrite each other's initial settings. [Standard initialization, lines 110–149](utils/accountPreferencesContext.js#L110) · [Standard writes, lines 188–242](utils/accountPreferencesContext.js#L188) · [Full-row serialization, lines 121–140](utils/accountPreferences.js#L121) · [Revision trigger](supabase/migrations/20261102055520_add_user_preferences_revision.sql#L12) · [Mixed writes](utils/mixedTrainerContext.js#L102)

### 11. Password recovery state can outlive the session that established it · Medium

The recovery marker is a tab-wide string. It is restored on startup, set by `PASSWORD_RECOVERY`, and cleared by `SIGNED_OUT` or a successful password change. A new `SIGNED_IN` or `INITIAL_SESSION` for a different user does not rebind or clear it. If a recovery was left unfinished and a different session is restored from shared auth storage, the reset form can accept the current user as if that session came from the earlier link. This is a wrong-account password-change flow using the current authenticated session. Bind recovery state to the recovered account/session and expire or clear it on identity changes. [Auth marker, lines 39–49 and 87–102](utils/supabaseAuthContext.js#L39) · [Reset form gate and write, lines 15–34](pages/reset-password.js#L15) · [Pinned auth client](https://raw.githubusercontent.com/supabase/supabase-js/v2.99.1/packages/core/auth-js/src/GoTrueClient.ts)

### 12. Signup reveals whether an email already has an account · Medium

The signup handler detects the zero-identity response shape and duplicate error text, then explicitly displays that the email is registered. When the provider returns the obscured response shape that this code recognizes, the UI reverses that privacy protection. Use uniform confirmation guidance and offer the same login and recovery links for either result. Verify the account-creation settings separately because they determine which provider response can occur. [Signup response classification, lines 23–35](pages/signup.js#L23) · [User-facing branch, lines 98–118](pages/signup.js#L98) · [Auth signup reference](https://supabase.com/docs/reference/javascript/auth-signup)

### 13. The custom calculator evaluates unbounded expressions on the main thread · Medium

The admin-only calculator runs parsing, evaluation, and exact result formatting synchronously inside the form handler. The allowlist checks syntax and operations but sets no bound on expression length, nesting, exponent size, or result size. Even supported arithmetic can therefore make the trainer unresponsive and prevent the UI from rendering its working state. The risk established here is local availability for the calculator user. Bound the accepted work and output size, and move evaluation to a worker that the UI can terminate. Runtime latency and thresholds were unmeasured. [Form and synchronous call](pages/index.js#L1233) · [Syntax checks](utils/aiMath.js#L118) · [Exact evaluation and formatting](utils/aiMath.js#L169) · [Solver entry point](utils/aiMath.js#L255)

### 14. Standard can discard a submitted answer if next-question generation fails · Medium

Standard creates the current attempt, then synchronously generates the next problem before it returns the attempt to the page for checkpointing. Decimal subtraction and division have explicit generator failure paths. If a valid answer is entered before the last question and the next generator throws, the error summary receives only the previous attempts and omits the session ID, so the newly submitted answer never reaches either persistence path. Commit the accepted attempt before generating the next question and keep the original session ID on the error path. [Attempt and next problem, lines 116–154](utils/trainerRound.js#L116) · [Generator failure paths](utils/mathEngine.js#L375) · [Submit catch and checkpoint, lines 922–970](pages/index.js#L922) · [Error summary, lines 593–629](pages/index.js#L593)

### 15. Standard rebuilds the full prompt history on every submission · Medium

For each non-final question the code copies the growing attempt array and makes a `Set` of all previously used prompts. Only positive exponentiation consults that set. The Standard UI allows a 10,000-question round, so ordinary addition, subtraction, multiplication, division, and decimal practice incur quadratic cumulative copying and the unused prompt-key work. Build and maintain a prompt index only where the generator uses it. Also avoid full-history recomputation in the per-answer state and summary path. This is a source-derived complexity finding. Wall-clock impact was unmeasured. [Maximum round size](utils/mathEngine.js#L1) · [Prompt keys](utils/trainerRound.js#L63) · [Submission path](utils/trainerRound.js#L101) · [Live statistics](pages/index.js#L328)

### 16. Browser Back and Forward change the history stack even when the round continues · Medium

`beforePopState` responds to a traversal by pushing a new copy of the current route before showing the dialog. After Back, pushing from the older entry truncates the existing forward history. Cancelling can restore the displayed URL while losing later entries. Confirming then uses `router.push(as)` instead of completing the original traversal, so a confirmed Back adds another entry and users can return to the round they just left. Restore the original history position on cancel and complete the original traversal on confirm. [History handler, lines 344–357](components/SiteLayout.js#L344) · [Navigation acceptance criteria](docs/plans/2026-09-23-high-priority-experience-fixes.md#1-explicit-end-round-and-navigation-behavior) · [Pages Router contract](https://nextjs.org/docs/pages/api-reference/functions/use-router#routerbeforepopstate) · [HTML navigation and session history](https://html.spec.whatwg.org/multipage/browsing-the-web.html)

### 17. Global letter shortcuts lack an accessibility control · Medium

The shared window listener runs plain-letter actions, including route switches and sign-out. It ignores interactive targets and accepts an ordinary letter elsewhere in the document. The Command Desk lists shortcuts but offers no way to turn them off or remap them. WCAG 2.2 criterion 2.1.4 requires an off switch, remapping to include a nonprinting key, or activation only while the relevant component has focus. Provide one of those mechanisms and verify speech-input and keyboard use. [Key definitions and eligibility](utils/hotkeys.js#L20) · [Global listener](components/SiteLayout.js#L413) · [Shortcut reference](components/CommandDesk.js#L419) · [WCAG 2.2 character-key shortcuts](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)

### 18. The Android updater stops before checking a compatible release · Medium

The archived updater chooses the first stable Android release with a manifest in the first 20 release results. An incompatible SDK, an incomplete asset list, or a version no higher than the installed version ends the check, even when later results contain a compatible update. A focused JavaScript check loaded the archived module with a mocked native bridge. For a mocked API 29 device, the module saw an API 30-only release followed by a valid API 24 release, requested only the first manifest, and returned an error with no update. Paginate as needed and choose the highest verified version compatible with the installed app. Retain native signature, size, hash, package, and version checks. The release 1.0.5 manifest itself specifies API 24. ### 21. Mixed paste can turn an invalid answer into an accepted answer · Low

The desktop paste handler removes every nondigit before invoking the auto-submit path. As a result, pasting `-12` into a question whose answer is `12` can earn credit for the unsigned value. Normal integer validation rejects the signed string. Validate the entire trimmed clipboard text before changing the input or triggering auto-submit. [Paste handler](pages/mixed.js#L816) · [Automatic submission](pages/mixed.js#L772) · [Integer validation](utils/mathEngine.js#L594)

### 22. Guest appearance reports a save when storage rejects it · Low

When the browser blocks storage or a write fails, `writeStorageJson` returns `false`. The preference providers ignore that result and report success. The Command Desk uses the success result to announce “Interface saved.” The guest sees the optimistic choice until reload, when the persisted preference is missing or unchanged. Pass the storage result back to callers and describe the selection as temporary when persistence fails.
